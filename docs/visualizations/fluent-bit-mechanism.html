What just happened?

Read these alongside the moving copies. All messages are synthetic.

    Why have a queue if Linux already stores the logs?

    The DB says where the reader reached, not what was delivered. After reading a message, the agent may be unable to send it. The queue keeps the already-read copy for retry. Original Linux files may later rotate away. A bookmark cannot reconstruct a message that has disappeared, and a database alone does not protect an unsent RAM copy.

    How switching and restarting work here
    • RAM → disk with an old bookmark: choose RESUME or NEW. NEW deletes only the unused reading bookmark, with no backup. Both retain the disk queue.
    • Disk → RAM: disk queue and DB remain on disk, unused. The RAM reader starts with new entries.
    • Disk → disk: keep the active reading position and queue. A smaller cap that cannot fit the existing queue is rejected.
    • Restart: this example assumes unsent RAM copies are lost. Saved disk copies and DB positions survive. A real graceful shutdown may send RAM copies first; sudden-power-loss windows depend on synchronization.
    What is simplified?

    This is a mechanism model, not a Fluent Bit emulator or a VM performance estimate. Real Fluent Bit groups records into chunks, uses memory-mapped disk storage, batches database updates and has soft/bursting limits. Here reads and copies are individual tiles, teaching capacities and rates are independently reduced, and the gateway's own queue is simplified. Disk mode writes queue files as it buffers—not only after RAM fills. Rotation recovery here continues at the oldest retained source entry; a real expired journal cursor needs inspection of the agent's behavior. All profiles assume an ordinary process restart, not a failed disk or power loss.

    Profile presets are a snapshot of the host-agent settings.yml. This page does not read or modify that file, connect to your hosts, or change pod collectors.
